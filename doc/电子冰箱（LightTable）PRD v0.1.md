# 电子冰箱（LightTable）PRD v0.1

## 1. 产品概述

### 1.1 产品名称

电子冰箱（暂定名：LightTable）

### 1.2 产品定位

一款面向个人与小家庭的 AI 厨房管理产品，通过“识别家中现有食材—理解用户健康目标—生成可执行的做饭与采购建议”这一闭环，减少食材浪费，降低做饭决策成本，并提升日常饮食管理效率。

### 1.3 一句话描述

它不是一个只会记库存的冰箱助手，而是一个能理解“我家现在有什么、我该吃什么、还缺什么、什么时候会坏”的 AI 饮食决策中枢。

### 1.4 产品愿景

让用户不再为“今晚吃什么”“冰箱里还有什么”“这些菜会不会坏”“买菜要买什么”而反复消耗精力，把冰箱从被动储藏空间变成主动协助生活的智能节点。

------

## 2. 背景与问题定义

### 2.1 背景

在真实家庭场景中，用户的饮食管理往往被切割在多个动作中：买菜、收纳、记忆库存、查看保质期、搜索菜谱、规划下一顿、补货。现有工具通常只覆盖其中一个点，例如：

- 外卖/买菜平台解决“买什么”
- 菜谱 App 解决“怎么做”
- 记账/清单 App 解决“记下来”

但没有一个产品能真正围绕“家庭现有食材”来进行统一决策。因此，用户经常出现：

- 冰箱里明明有东西，但想不起来
- 买重复食材，造成浪费
- 快过期才发现，来不及处理
- 有材料但不会组合成一顿饭
- 减脂、控糖、增肌等健康目标与现有库存脱节

### 2.2 核心痛点

1. **库存不可见**：用户不知道家里具体还有什么。
2. **保质期不可控**：用户无法及时感知哪些食材即将过期。
3. **决策成本高**：即使知道有什么，也不知道能做什么。
4. **采购与库存脱节**：采购行为没有与现有库存形成闭环。
5. **健康目标难执行**：饮食建议与个人目标、忌口、偏好缺乏结合。

### 2.3 核心机会

如果产品能把“库存识别 + 用户约束理解 + 餐食生成 + 补货建议”串成闭环，就能从单点工具升级为高频、强留存的生活助手。

------

## 3. 目标用户

### 3.1 目标用户画像

#### 用户类型 A：独居青年 / 学生

- 做饭频率中低
- 冰箱容量有限，常忘记已有食材
- 容易冲动买菜或点外卖
- 核心需求：快速决策、少浪费、低操作成本

#### 用户类型 B：小家庭用户

- 冰箱中食材种类多
- 多人共同使用冰箱，库存混乱
- 需要兼顾营养、预算与孩子/家人口味
- 核心需求：库存清晰、家庭协同、每周餐食规划

#### 用户类型 C：健康管理用户

- 有减脂、增肌、控糖、低盐等明确目标
- 更关注食材营养信息与可替代建议
- 核心需求：基于库存给出符合目标的饮食方案

### 3.2 非目标用户

- 高度专业的餐饮门店库存管理者
- 需要复杂 ERP、供应链管理的商业厨房
- 只想看静态菜谱、不需要库存管理的用户

------

## 4. 产品目标

### 4.1 业务目标

1. 建立“库存驱动型饮食决策”产品定位
2. 提升用户日活和周活，形成高频厨房使用场景
3. 验证 AI 在家庭饮食管理中的实际价值，而不只是聊天问答

### 4.2 用户目标

1. 用最少步骤完成库存录入
2. 快速知道哪些食材优先处理
3. 在 1 分钟内得到适合当前库存的餐食建议
4. 自动生成补货清单，减少重复购买与遗漏购买

### 4.3 成功指标（MVP）

- 食材录入成功率 > 85%
- 首次完成一次“录入库存→获得菜谱建议”的用户比例 > 60%
- 每周至少使用 2 次库存查看/菜谱推荐功能的用户比例 > 35%
- 用户主动处理临期食材的转化率 > 25%

------

## 5. 核心使用场景

### 场景 1：不知道今晚吃什么

用户打开产品，希望系统基于现有库存快速推荐几道菜，而不是从零开始搜索。

### 场景 2：买菜前确认家里缺什么

用户准备去超市/买菜平台下单，希望先知道家里还有什么，避免重复买。

### 场景 3：发现食材快过期

系统提醒用户牛奶、菠菜、鸡蛋即将到期，并给出“优先消耗方案”。

### 场景 4：围绕健康目标吃饭

用户设置“减脂、高蛋白、晚餐 500 kcal 内”，系统需要在现有库存约束下生成合适菜谱。

### 场景 5：家庭成员共同维护冰箱

A 放入食材，B 能看到最新库存；系统记录来源、时间和建议用途。

------

## 6. 核心价值主张

### 对用户的价值

- **省脑力**：不再每天重复想“吃什么”
- **省钱**：减少重复购买和食材浪费
- **更健康**：建议与健康目标绑定
- **更有掌控感**：冰箱状态清晰可见

### 对产品的差异化价值

与菜谱 App 相比，它从“家里已有食材”出发；
与清单 App 相比，它能主动给出吃法与补货建议；
与通用 AI 助手相比，它具备持续库存记忆与厨房场景理解。

------

## 7. 产品范围

### 7.1 MVP 范围

MVP 聚焦 4 个闭环：

1. 食材录入
2. 库存展示
3. AI 菜谱推荐

- 商业化配送闭环
- 复杂营养师级别分析
- 多语言国际化

## 8. 功能设计

## 8.1 模块一：食材录入

### 目标

用尽可能低的操作成本建立库存。

### 输入方式

1. 手动输入
2. 自然语言模糊输入（如“买了两盒低脂牛奶和一点生菜”）
3. 拍照识别食材
4. 上传购物小票 / 订单截图识别
5. 从历史采购记录一键导入（后续）

### 关键字段

- 食材名称
- 品类（蔬菜 / 肉类 / 奶制品 / 调味品等）
- 数量
- 单位
- 购买/放入时间
- 预计保质期
- 存储区域（冷藏 / 冷冻 / 常温）

### 功能说明

- 当用户上传图片、订单或输入自然语言后，系统自动抽取候选食材并供确认
- 支持模糊数量，如“半盒”“一袋”“约 300g”
- 支持模糊食材名称识别，如“圣女果/小番茄”“生菜/油麦菜”“牛奶/低脂奶”等非标准表达
- LLM 先对用户输入进行语义解析与标准化，提取食材名、数量、单位和修饰信息
- 系统将标准化后的食材与数据库中的标准食材表进行相似度匹配，找到最相近的已有食材实体
- 若匹配成功，则合并到对应库存并进行数量换算；若匹配不确定，则返回多个候选项供用户确认
- 支持合并已有库存，例如再次购入鸡蛋时合并数量

### 设计原则

- AI 先识别，用户后确认
- 允许模糊输入先进入解析流程，再映射为标准化库存实体
- 允许不完整信息先入库，后续逐步补全
- 优先保证录入速度，而非一次性完美准确

------

## 8.2 模块二：库存管理

### 目标

让用户清楚知道“现在家里有什么”。

### 核心功能

1. 按分类查看库存
2. 按临期程度排序
3. 查看单个食材详情
4. 手动扣减 / 标记已用完
5. 查看新增、即将过期、库存不足的汇总卡片

### 页面关键展示

- 今日临期
- 推荐优先吃掉的食材
- 冰箱当前总食材数
- 缺货常用品提示

### 设计重点

- 首页不是单纯列表，而是“可行动的库存概览”
- 优先把用户最需要处理的信息放前面：临期、浪费风险、可做菜数

------

## 8.3 模块三：AI 菜谱推荐

### 目标

基于库存、偏好和目标，生成当前可执行的餐食方案。

### 输入条件

- 当前库存
- 就餐人数
- 时间约束（如 20 分钟内）
- 用户目标（减脂 / 高蛋白 / 清淡）
- 忌口与偏好（不吃辣 / 不吃牛肉 / 喜欢汤类）

### 输出内容

- 推荐菜品名称
- 推荐理由（用了哪些临期食材 / 符合什么目标）
- 所需食材清单
- 缺失食材清单
- 步骤说明
- 可替代方案

### 推荐策略

优先级可按以下原则综合排序：

1. 优先消耗临期食材
2. 尽量减少缺失食材
3. 满足用户健康目标
4. 控制操作复杂度与烹饪时长

### 示例

输入：鸡蛋、番茄、豆腐、半盒牛奶；目标：减脂晚餐
输出：番茄豆腐蛋花汤、煎豆腐配番茄炒蛋等

------

## 8.4 模块四：临期提醒与消耗建议

### 目标

把“被动发现浪费”变成“主动提前处理”。

### 核心功能

- 临期提醒
- 风险等级（高 / 中 / 低）
- 一键生成“今天先吃这些”的建议
- 结合菜谱推荐优先消耗

### 提醒逻辑

- 高风险：1 天内到期 / 明显已放置过久
- 中风险：2~3 天内到期
- 低风险：正常状态

### 输出形式

- 首页提醒卡片
- 消息提醒（后续）
- 每周冰箱体检报告（后续）

------

## 8.5 模块五：补货清单

### 目标

让采购和库存打通，形成闭环。

### 生成逻辑

补货建议来源包括：

1. 用户已用完的常用食材
2. 多次被推荐但缺失的关键食材
3. 用户主动收藏的常备食材
4. 一周餐食计划所需缺口

### 功能说明

- 自动生成补货清单
- 支持手动编辑
- 支持区分“必买 / 可选”
- 支持导出到买菜清单

------

## 8.6 模块六：用户档案与偏好设置

### 内容

- 饮食目标：减脂 / 增肌 / 控糖 / 均衡饮食
- 忌口：过敏原、不吃的食材
- 偏好：中餐/西餐、热菜/凉菜、重口/清淡
- 常备厨房设备：空气炸锅、烤箱、微波炉等
- 家庭人数

### 作用

使推荐更具连续性和个性化，而不是每次重新提问。

------

## 9. 用户流程

## 9.1 首次使用流程

1. 用户进入产品
2. 选择家庭人数、饮食目标、忌口
3. 通过拍照/手动/订单导入录入首批食材
4. 系统生成库存首页
5. 系统给出第一批菜谱推荐与临期提醒

## 9.2 日常使用主流程

1. 用户查看首页库存状态
2. 选择“今晚吃什么”
3. 系统生成可做菜品
4. 用户选择一道菜
5. 查看步骤与缺失食材
6. 做饭后系统扣减库存

## 9.3 买菜前流程

1. 用户打开补货清单
2. 查看缺失与常备食材
3. 一键导出采购建议
4. 买完后通过小票/订单导入更新库存

## 11. 推荐与智能能力设计

### 11.1 AI 能力边界

本产品中的 AI 主要负责：

1. 食材识别与信息抽取
2. 基于库存的菜谱生成与排序
3. 临期风险判断
4. 补货建议生成

### 11.2 不由 AI 决定的部分

- 最终库存写入需要用户确认
- 高风险健康建议不做医疗级承诺
- 保质期判断以保守建议为主，不替代食品安全判断

### 11.3 核心体验要求

AI 不是单纯聊天框，而应以结构化结果交付：

- 清楚列出用了哪些食材
- 缺什么
- 为什么推荐
- 怎么做

## 13. 非功能需求

### 13.1 易用性

- 新用户 3 分钟内应完成首次录入并看到结果
- 高频操作不超过 3 次点击

### 13.2 准确性

- OCR / 识别结果需支持人工校正
- 关键识别字段错误时要可快速修改

### 13.3 性能

- 首页加载 < 2 秒
- 菜谱推荐结果返回 < 5 秒

### 13.4 隐私与安全

- 用户图片与订单数据需安全存储
- 用户饮食偏好与家庭信息仅用于个性化推荐

------

## 14. 风险与边界

### 14.1 主要风险

1. 食材识别准确率不稳定，影响首印象
2. 用户不愿持续手动维护库存，导致数据快速失真
3. 菜谱推荐若脱离真实做饭习惯，会显得“聪明但没用”
4. 保质期判断不够可靠时，容易引发信任问题

### 14.2 对应策略

1. 采用“AI 识别 + 用户确认”机制
2. 优先接入低成本录入方式，如订单/小票导入
3. 菜谱优先考虑简单、常见、真正能做的方案
4. 对食品安全采用保守提示，不给绝对判断

## 17. 竞品与差异化（简版）

### 菜谱类产品

优势：内容丰富
不足：不理解用户当前库存

### 清单/记账类产品

优势：记录清晰
不足：缺乏智能决策

### 通用聊天式 AI

优势：自然语言交互灵活
不足：缺乏持续状态管理与结构化厨房场景设计

### 本产品差异化

从“库存状态”出发，而不是从“用户提问”出发。

## 18. 技术实现建议（面向 vibecoding）

### 18.1 推荐技术拆分

前端：Web / 移动端轻应用
后端：用户、库存、推荐记录、任务流管理
AI 层：OCR、食材抽取、推荐生成、规则排序
数据库：用户信息、库存状态、菜谱库、推荐日志

### 18.2 适合 vibecoding 的开发原则

1. 先把流程打通，再优化模型效果
2. 先做伪数据和规则，再逐步接入 AI
3. 先保证页面和状态管理清晰，再追求复杂 Agent 架构
4. 每个功能都要可以被独立 demo

### 18.3 最小可跑通链路

上传订单截图 → 识别食材 → 写入库存 → 生成 3 个推荐菜谱 → 标记临期食材 → 生成补货清单

3. 我们的核心卖点更偏“健康管理”还是“库存驱动做饭决策”？
4. 是否考虑家庭多人协同作为第一阶段能力？
5. 是否需要接入真实菜谱数据库，还是先用 LLM 生成？

------

## 20. 总结

电子冰箱的核心不是“把冰箱数字化显示出来”，而是围绕家庭现有食材建立一个真正可执行的饮食决策闭环。MVP 阶段最重要的不是把所有功能都做全，而是验证一件事：用户是否愿意因为它更轻松地决定吃什么、处理临期食材和安排补货。

只要这个闭环成立，后续无论是健康管理、家庭协同，还是与买菜平台和硬件的连接，都有明确扩展空间。
